# ADR-303：Git 控制合并为一个始终可按的主按钮与分组面板，分叉用 rebase 修复

- 关联：ADR-083、ADR-084、ADR-293

## 背景

ADR-084 与 ADR-293 让右上角的 Git 主按钮推荐下一步，但按钮和菜单留下了几个问题。落后、分叉、冲突和状态未知时主按钮是禁用标签，修复动作藏在下拉里；
可合并的 PR 同时显示带下拉的“查看 PR”和单独的“合并 PR”两个按钮；没有推荐时只剩一个无文字的分支图标。菜单是最多 12 行的平铺列表，
合并方式占六行，不可用的行只在点击后用提示说明原因；“重置工作区”与“本地合并”“创建 PR”同样式并排，“本地合并”也没说明并入哪个分支。
分叉分支的修复是“拉取并推送”，它调用宿主的裸 `git pull`，近期的 Git 在没有配置分叉合并方式时会直接拒绝。

## 决策

1. 主按钮始终是可以按下的动作。取第一个匹配的状态：冲突（本地冲突，或打开的 PR 报告冲突且没有可推送的提交）、提交、分叉时的“变基到远端”、仅落后时的“拉取”、
   状态未知、打开的 PR 上的推送或合并 PR、查看 PR、创建 PR、基础分支上的推送、重置工作区、无事可做。ADR-084 第 1 条的“落后或分叉显示禁用状态”被取代：
   “提交”排在分叉和落后之前，因为变基与拉取都需要干净的工作树。冲突与状态未知只打开面板；一键修复不适用时，按钮显示状态名（“已分叉”“落后于远端”）并打开面板，不再是禁用标签。
2. 主按钮上的动作不能执行时，落到表中的下一行，而不是显示一个按下无效的动作。判断由客户端的规则做出，不是宿主的回答：打开的 PR 需要推送而推送行不可用
   （例如落后于 upstream）时显示“查看 PR”，不会显示“合并 PR”。
3. 打开的 PR 现在可以合并时，主按钮直接合并并使用已记住的合并方式，单独的快速合并按钮取消。ADR-084 与 ADR-293 中没有主按钮时只显示菜单入口的规则，
   改为带文字的“已是最新”（干净且已同步）或“Git”按钮。判断“已交付”和推荐重置的条件不变。
4. “拉取”只在配置的 upstream 与计数所用的远端引用一致（`upstreamRef` 等于 `branchStatus.remoteRef`）时作为主按钮出现，避免按钮显示一个引用的计数却拉取另一个。
5. 菜单改为分组面板，变更面板的 Git 菜单原样复用：只读状态摘要，随后依次是变更、同步、Pull request、本地（并入基础分支，菜单项写明分支名），
   重置工作区单独放在最后并使用破坏性样式。Pull request 组在不在基础分支上或存在打开的 PR 时显示，使主按钮上的动作总能在自己的分组里找到；本地组只在不在基础分支上时显示。
   不能执行的动作禁用并在行内说明原因，不再事后弹出提示；有打开的 PR 就显示“合并 PR”，不能合并时说明原因（草稿、冲突、未就绪、合并队列），而不是让行消失。
   命令面板只列出会执行操作的动作，不收录仅打开面板的状态按钮，不可用动作的原因仍以提示显示。
6. 合并方式在面板中只有一行，进入子页选择仓库允许的方式；打开的 PR 允许多于一种方式时才显示。Forge 没有报告合并能力时，三种方式都提供，与改版前一致。
   选择按宿主和项目记在设备上，不进入项目设置，也不同步；已记住的方式不再被允许时，依次回退到允许的 squash、merge、rebase。
   该方式用于按钮和面板里的合并 PR，以及开启自动合并。关闭自动合并的行标为“禁用自动合并”。
7. 新增协议操作 `checkout.rebase.request` / `.response`，形状与 `checkout.pull` 相同，客户端不传引用。宿主自行解析目标，复用 `branchStatus`
   的规则：优先远端（有 `origin` 用 `origin`，否则第一个远端）上的同名分支，因此动作总是作用于按钮所显示的状态。
   宿主分别用不同错误拒绝：已有进行中的 rebase、merge、cherry-pick、revert，或暂停的 cherry-pick、revert 序列；不在分支上；没有远端；已跟踪文件有改动；
   推送会发往该远端分支以外的位置。推送目标按 `push` 的解析一路追到最后的回退（回退到 `origin`），所以首个远端不是 `origin` 的仓库，只有分支跟踪该远端时才能变基。
   这些都发生在 fetch 之前；fetch 只更新目标分支的远端跟踪引用，fetch 之后远端分支不存在同样拒绝，其他 fetch 失败按 Git 的原错误返回。
   通过检查后执行 `git rebase --rebase-merges --no-fork-point <ref>` 并关闭 `rebase.updateRefs`，因此不移动任何其他本地分支。保留合并提交，
   否则本地合并过基础分支的分支会用新 ID 重建基础分支的提交；`--no-fork-point` 避免 fork-point 模式丢弃只存在于远端跟踪引用 reflog 中的提交。
   成功之后，宿主检查被 rebase 替换的每个提交：若有已离开分支历史、又被某个远端跟踪引用包含的提交，就把分支重置回原位并拒绝，错误为
   `Rebasing would duplicate commits that are already published, so this branch cannot be rebased here`。“已发布”指本次调用 fetch 之后被本地远端跟踪引用包含。
   最常见的情形是分支推送之后又在本地变基到基础分支；它的出路是 force-push，不在本决策范围内，所以这种状态被拒绝而不是被修复。
   rebase 中途停下时执行 `git rebase --abort` 回到操作前的提交；只有停下时留有未合并路径才以合并冲突报告，否则返回 Git 自己的错误。拒绝与 fetch 失败不中止任何东西。
   该操作不推送，成功后分支只领先，主按钮转为普通的“推送”。不改写已在远端的提交，也不提供 force-push 流程；变基到基础分支不在范围内。
   客户端从宿主公布的方法列表判断是否支持，不支持时不提供变基，也没有拉取回退；客户端按 `upstreamRef` 缺省或等于 `branchStatus.remoteRef` 决定是否提供，以宿主检查为准。
   “拉取并推送”在按钮、面板、命令面板和文案中全部移除。
8. 重置工作区处于“已交付”状态时，确认文案缩短为“你的工作已合并。要将此工作区重置到最新的 {base} 吗？”；其他状态保留完整警告。
   重置的服务端行为、可用条件和 ADR-293 第 3、4 条的推荐条件不变。

## 后果与验证

旧宿主没有 `checkout.rebase.request`，分叉分支只显示状态并打开面板，用户需要自己处理；已推送后又在本地变基到基础分支的分支同样被拒绝，需要在本功能之外 force-push。
主按钮和菜单文案改变，浏览器测试用的测试 ID 保留。`crates/filesystem` 的本地 Git 测试覆盖各项拒绝、冲突后恢复原提交、保留本地合并和重复已发布提交时的拒绝；
客户端测试覆盖按钮顺序与回退、合并方式的记忆、面板分组与行内原因，以及重置确认的两种文案。
