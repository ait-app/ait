# ADR-225：微信与 QQ Channel 的扫码接入

- 沿用：[ADR-224](adr-224-feishu-scan-onboarding-and-stored-secrets.md) 的 daemon 直连扫码、状态请求驱动与 Secret 保存边界。

## 背景

用户希望像飞书一样扫码把微信和 QQ 接入 Workspace Bot。预期用法是用户本人给 Bot 发消息：微信只用单聊，QQ 用单聊和群聊。
两个平台都能由 daemon 直接完成扫码，不需要中心服务，但都依赖未公开的接口，且各有与飞书不同的限制。

## 决策

1. 微信使用 iLink Bot 接口：扫码返回 Bot Token、Bot ID、接口地址和扫码者 ID。Channel 只接受扫码者的单聊，不提供群聊选项，也没有手动接入，因为 Token 只能由扫码取得。
2. QQ 使用官方机器人网关（`C2C_MESSAGE_CREATE` 与 `GROUP_AT_MESSAGE_CREATE`）。扫码通过 `q.qq.com` 的绑定任务完成：daemon 生成 AES-256 密钥，QQ 用它加密返回的 AppSecret。手动填写 App ID 与 AppSecret 作为回退，daemon 向 QQ 验证后保存。
3. 凭据沿用 ADR-224 的存储和引用规则。微信接口地址来自扫码响应，只接受 `*.weixin.qq.com` 的 HTTPS 地址，否则 Token 可能被发往任意主机。
4. QQ 文档没有说明单聊 `user_openid` 与群成员 `member_openid` 是否相同，`union_openid` 又可能为空，因此不能假定扫码者在群里可被识别。QQ Channel 可在设置页生成一次性配对码（8 位，10 分钟有效，仅保存在内存中）。把它私聊发给机器人，或在群里 @ 机器人并发送它，发送者即加入允许列表。手动接入的 Channel 起初没有允许的发送者，用同样方式完成配对，所以 QQ 是唯一允许空发送者列表的类型。生成配对码的方法属于写操作，访客不可调用。
5. QQ 只使用带 `msg_id` 和 `msg_seq` 的被动回复。官方文档写明群聊 5 分钟、单聊 60 分钟，每条消息最多回复 5 次；窗口过期、次数用尽或回复来源缺失时不再尝试主动消息，并按现有规则记为投递不确定。
6. 微信回复需要携带入站消息的 `context_token`。它作为 Turn 的 `reply_to` 持久化，daemon 重启后未完成的回复仍可使用，因此 `reply_to` 的长度上限放宽到 4096 字节。Token 过期时不带它重发一次。
7. 微信的 `get_updates_buf` 是不透明字符串，保存在新增的 `Channel.syncToken`，只在本批消息入队后推进，且不返回给客户端。
8. `bot.channel.types` 继续只返回旧列表，客户端根据方法能力显示微信与 QQ。旧客户端按枚举校验这个响应，新增取值会使它们无法添加任何 Channel。
9. 只支持文本消息，不支持 QQ 频道。

## 后果

- 两个扫码流程和微信收发都依赖未公开接口，平台修改后可能失败；QQ 可用手动接入，微信没有回退。微信个人账号使用此接口的条款风险未经确认。
- QQ 网关断开期间的消息会丢失，因为重连时不恢复旧会话；已入队的消息不受影响。
- 配对后 Channel 配置改变，连接会重建一次。确认消息先于保存发送，否则重建会中断它；保存失败时用户需要重新配对。
- 创建过微信或 QQ Channel 后回退到旧版 daemon，目录会因未知类型而无法加载。删除这些 Channel 不能解决，因为已删除的 Channel 仍保留在目录中。旧客户端也无法解析包含这些类型的 Channel 列表。
- 微信轮询失败时在连接内重试，不重建连接，否则会回到启动时的位置。收发任一方中断时，正在发送的回复按现有规则记为投递不确定。
- 2026-11-09 实现时仅用模拟服务验证，尚未用真实账号验证。
