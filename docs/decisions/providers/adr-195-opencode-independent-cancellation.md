# ADR-195：OpenCode 独立取消信号与确认期限

- 状态：Accepted
- 日期：2026-10-27
- 修订：[ADR-115](adr-115-opencode-acp-provider.md) 的取消准入和失败清理规则。

## 背景

OpenCode 的执行器同时负责消费 ACP、发布有界输出和回放结束历史。原来停止请求通过
同一个执行器的命令队列发送，调用方等待其确认。输出队列满时，执行器等待宿主消费；
宿主又在等待执行器处理取消。原生已经完成、执行器等待历史回放时也会阻塞停止请求。
此外，原生完全缺少 `session/prompt` 终态时，发送取消后没有确认上限。

官方 OpenCode 2.1.3 的 ACP 只有取消通知及关联 prompt 结果，没有 OMP 的
`get_state.isSettled` 接口。它自己的取消清理可等待五秒；正文输出结束仍不能代替结果。

## 决策

1. 每个活动回合拥有独立的 watch 取消信号，记录首次请求时间。停止只设置该信号，
   不等待输出队列、控制回复或原生清理；重复点击不重置时间、不重复发送原生通知。
   ACP 执行器恢复消费时优先发送 `session/cancel`。审批拒绝并中断也使用同一信号。
2. 接受停止后，宿主继续消费输出、问答和最终历史。新回合创建全新的信号，迟到的停止
   不影响下一轮。已收到关联原生结果的回合，回放后保留该成功、失败或取消结果。
3. 活动执行器超过十秒仍未完成取消确认及收尾时，返回明确的取消确认失败，
   上限不超过原有控制期限。十秒为原生五秒清理预留余量，不是模型运行期限。
   已完成的执行器不因宿主迟到消费而被改成超时。
4. 确认失败后中止唯一执行器，等待其退出并回收受管进程组。已经报告的回合失败与
   进程清理确认分别处理：清理成功后允许宿主持久化 error、发布终态并清除 running。
   清理超时仍返回失败。取消错误在关闭后保留，供时间线和持久状态使用。
5. 完全没有关联终态时，通过显式停止有界报错退出；不从文字、用量更新或静默时间
   推断成功，不启用未验证的 HTTP 状态接口、不自动重发输入。下一次显式输入通过
   既有原生恢复路径继续，ACP 仍是执行、取消和完整历史的唯一通道。

## 验证

离线夹具覆盖满输出队列、结束历史回放阻塞、重复停止、原生拒不取消、终态响应丢失、
宿主延迟消费、错误持久化及下一次输入恢复。前两项在旧逻辑下稳定超过停止请求期限。
官方安装版使用隔离配置、原生数据库及 loopback 模型，代理只丢弃一次 prompt 结果，
验证实际输出已完成时仍能停止并恢复历史；不修改安装、不读取用户认证、不调用付费模型。

[取消与结算](https://github.com/anomalyco/opencode/blob/bb25a2f4a3f3f04d7c344bec0c0574ea3510b3b1/packages/cli/src/acp/turn.ts)。
