# ADR-310：Host 账号用量按 Provider 活动刷新

## 背景

中心对每台在线 Host 约每 70 秒读取一次 `provider.usage.list`（成功后 60 秒，加 5 秒调度粒度）。
ADR-219 的 Host 快照超过 60 秒即后台刷新，读取周期恰好略长于此阈值，于是每次读取都触发一次原生查询。
实测一台 Host 对 Codex `account/rateLimits/read` 平均每 72 秒一次，约每天 1200 次；Claude 走同一路径。
无人查看、无 Agent 运行时也不停；同一账号登录多台 Host 时次数相加，而上游按账号限流。

错误快照只复用 15 秒，短于读取周期。Codex 的限流错误不带重试时间，ADR-285 只约束带 `nextRefreshAt`
的报告，所以每次读取都重试；失败的读取还丢弃查询进程，曾连续八次“启动进程后被限流”。

## 决策

1. Host 快照是否过期由活动决定，不由年龄决定。`AgentManager` 为每个 Provider 维护活动计数：会话的每次调用开始、
   每个请求用量和调用结束各计一次，与用量账本共用同一组钩子，Host 没有账本时照常计数。读取开始时记下计数；
   之后计数变化，或快照中某个窗口的 `resetsAt` 已过，快照即为过期。读取期间发生的活动因此仍算过期。
2. 非强制读取：过期的快照只回答 5 分钟，未过期的回答 30 分钟，后者限定其他设备消耗额度后本机仍显示旧值的时间。
   此后的读取等待一次共享的新查询，不再先返回旧快照再后台刷新：客户端读取后不会再读一次，后台结果到不了它手里。
   查询仍独立于读取方的连接。无法验证凭据源的 Provider 仍逐个读取核对原生身份，不合并查询，核对后套用同一规则。
   手动强刷不变。
3. 会话快照不观察活动，仍只保留 5 分钟：它由用户打开会话详情触发，不受中心读取影响。
4. 失败的读取按连续失败次数退避，60 秒起每次翻倍，最长 15 分钟且不超过该缓存保留快照的时间，成功后清零。
   退避只约束非强制读取；ADR-285 的上游重试时间继续同时约束强刷，两者都满足后才重新查询。
5. Codex 查询进程在上游限流后保留，并继续复用已核对的账号；是否限流只看这次请求自己的拒绝，不看进程的其他输出。
   其他拒绝、传输失败、超时和取消仍丢弃进程，让状态异常的进程在下次读取时重建。
6. 中心把成功采集间隔从 60 秒改为 5 分钟（ait-server）。两处各自生效：旧 daemon 靠中心间隔降到每小时 12 次，
   新 daemon 的查询次数不再取决于任何调用方的读取频率。

## 后果

修订 ADR-219 的 60 秒与 300 秒阈值、先返回旧快照的后台刷新和 15 秒错误缓存，以及 ADR-285 第 2 项在截止时间后恢复的缓存策略。

空闲 Host 的每个 Provider 每小时约 2 次原生查询，持续工作时至多 12 次，原为约 50 次。Provider 有活动后，
读取得到的数据不早于 5 分钟前；空闲时最多滞后 30 分钟，手动刷新立即取得新值。代价是工作中每 5 分钟有一次读取
要等上游返回，通常几秒，查询本身受 25 秒截止时间约束；中心的周期读取通常替客户端承担了这次等待。

通过临时环境以其他账号运行的会话也计入该 Provider 的活动：它工作期间，Host 账号按工作中的频率刷新。

会话在轮次中已经收到原生额度通知（例如 Codex 的 `account/rateLimits/updated`），本决策没有使用它；
用它更新快照可以去掉剩余的查询，留给后续工作。
